# AmnPM audit — 2026-11-03

> **Historical snapshot.** This audit predates the current key domains, rename
> limits, and plain-language security pages. Counts, revisions, and test results
> are not current. It is kept for engineering history only.

Scope: every module under `tgcloud/`, the test suite, and a live end-to-end run
with two real Telegram accounts against the deployed bot. Severity: **BUG**
(wrong behavior), **RISK** (correct but fragile), **PERF**, **UX**, **TEST**.

## Platform limit: bot-DM topic titles

Verified live, including a 20-hour observation: `editForumTopic` returns success
and Telegram stores the new name (read back via `getForumTopics`), but Telegram
emits **no `messageActionTopicEdit` service message** for bot DMs, and clients
keep showing the creation-time title indefinitely. `closeForumTopic` /
`reopenForumTopic` are rejected in private chats ("not a supergroup forum"), so
there is no service-message lever. `deleteForumTopic` + `createForumTopic` would
show a new title but destroys the thread's history.

Consequences:
- `/rename` and memo renames update the bot/API record only; the client-visible
  title does not change.
- The confirmation now says "Topic name updated … for the bot" to avoid lying.
- A real visible rename requires replacing the topic (new thread, old history
  stays behind); that is a product decision, not implemented.

## Fixed in this audit

- **BUG** `topics.js topicDisplayName`: a decrypt failure fell back to the
  default name, and the memo renamer would then overwrite a custom topic label
  with that guess. It now returns `null` and the row is skipped (counted as a
  failed rename). Covered by a test.
- **BUG** `message.js` memo branch: a throw from `renameTopics` aborted the
  handler before clearing the memo state and confirming, leaving a stale prompt
  and no feedback. The call is guarded; the memo is still confirmed or reported.
- **BUG** (earlier in this session): duplicate memo labels made topics of
  different links indistinguishable and made memo edits look ignored.
  Uniqueness is enforced on create and on change; existing duplicates were
  cleaned in the live database.
- **BUG** Duplicate memo answers now suggest the first free label
  (e.g. `Try "link 2"`), for both `/newlink` and memo edits.
- **BUG** Late album stragglers paid no rate limit and, on a failed second
  delivery, sat without a prompt until the sweep. They now count against both
  delivery limits and the sender is told when part of the album was not sent.
- **BUG** A media message during a memo prompt re-sent the prompt for every
  album item. The prompt is no longer re-sent while its message id is known.
- **UX** An expired link-menu button says "This menu is out of date. Open
  /settings again." instead of "link not found".
- **UX** `/mode` now says the marker is cleared and every message still asks
  once, matching actual behavior.
- **BUG/UX** `/rename` answered "use it inside a topic" in three different
  situations. Live-tested contexts: anon and forward topics renamed correctly;
  messages in **All** now say "(not in All)"; a **stale topic** from an older or
  revoked link now says the topic is no longer linked, instead of claiming the
  user is not in a topic.

## Bugs / risks still open

1. **RISK** `queue.js`: `sent_ids` is persisted before `sendControls`. If
   controls fail after the media landed, the retry skips the media and sends
   controls again (duplicate controls, never duplicate media). Acceptable
   trade-off; document.
2. **RISK** `queue.js`: after a dead-topic recovery the old topic stays visible
   with its old name; Telegram offers no way to delete or rename a thread the
   bot no longer owns. Users must delete stale topics manually.
3. **RISK** `delivery.js aliasFor()` creates the history conversation *before*
   delivery is confirmed. If the sender abandons the tap, an empty conversation
   row remains. Harmless, but it inflates `conversations` over time.
4. **RISK** `store.js`: `retired_aliases` and `retired_tokens` grow without
   bound (required for "never reuse"). Only 8-byte fingerprints are stored.
5. **RISK** `links.js ownerSalt()` reads and decrypts the installation salt on
   every update (deliberate: a cached salt survives a database wipe and breaks
   every key). Cost is one read + one AES decrypt per update.
6. **RISK** aliases can collide across different links (uniqueness is per link
   by design). The owner of two links can see the same alias twice.
7. **RISK** `freshIndicator` gives up after 8 consecutive collisions; that path
   refunds and tells the sender delivery failed. Probability is negligible.
8. **RISK** `closeLinkTopics` cannot truly close a topic in a private chat;
   it appends `❌` to the name instead. The thread stays technically writable
   but the bot rejects writes after the link row is deleted.
9. **RISK** A link-menu message rendered earlier keeps buttons whose action
   tokens were deleted by a newer render (`menu.js` deletes `menu` tokens per
   render). Expired buttons now explain themselves, but the old message still
   looks actionable.
10. **RISK** Memo state is owner-wide: while a memo prompt is pending, any text
    that is not a known command becomes the memo.
11. **TEST** Live suite cannot read rich-message text (`sendRichMessage`),
    so `/help` and `/about` are verified as "replied", not by content.
12. **TEST** No live coverage for: forward mode, block-all, modes-disabled
    chooser, rate-limit messages, album partial notice, dead-topic recovery,
    stranded-job reaper, revoke while a memo prompt is pending.

## Performance

1. **PERF** Hot path: 11–12 SQL statements per sender message, ~21 per mode
    delivery (bench); the *mode* path is the most expensive.
2. **PERF** `isTopicNameTaken` decrypts every custom label of the owner on each
    rename (O(links × topics)). Bounded by the 10-link cap; fine now, quadratic
    if the cap grows.
3. **PERF** `memoInUse` decrypts every link memo on each create/change
    (O(links), ≤10).
4. **PERF** `sendControls` seals 4 action tokens per delivered batch; tokens
    live 30 days and are swept only on 2% of updates. Table grows with traffic.
5. **PERF** `drain` runs one `UPDATE` for stale claims on every drain, even when
    there is nothing to reap. A last-reap timestamp in `meta` would avoid it.
6. **PERF** `linksMenu` deletes and re-inserts a menu token per link on every
   render; up to 10 rows of churn per settings tap.
7. **PERF** Follower handlers in an owner album sleep `albumHoldMs +
   albumTakeoverMs` (2.5 s) before taking over; each follower holds an isolate.
8. **PERF** Aliases and three-word topics are computed by HMAC; negligible.

## UI / UX

1. **UX** Renames update Telegram's server state immediately, but bot-DM topic
   edits produce no `messageActionTopicEdit` service message, so clients can
   keep showing the old title until the chat is reopened. The bot cannot emit
   that service message; the in-topic confirmation is the only immediate signal.
2. **UX** An album that partially fails tells the owner ("part of the album was
   deleted") while the sender's confirmation still says sent. The sender is now
   told when a *late* straggler fails; a partially deleted source album still
   only notifies the owner.
3. **UX** Closed/revoked topics accumulate in the chat. Telegram keeps them;
   the bot can only mark them `❌`.
4. **UX** A stale link-menu button now explains itself, but the old message
   still looks actionable.
5. **UX** `/rename` outside a topic answers with usage, but in a dead/stale
   thread the same message appears even though the user is "inside a topic";
   explaining that the topic predates the current link would help.
6. **UX** Memo label is truncated to 20 chars in the button and 40 in the topic
   tail; two long memos sharing a prefix become indistinguishable.

## Security / privacy

1. Split-key actions verified: ciphertext is split, the 12-char suffix lives only
   in `callback_data` (72 bits), truncated GCM fails closed.
2. No application logging; `source.test.js` bans `console` everywhere except the
   word-data file.
3. No plaintext chat ids, tokens, memos, labels, or message text are stored
   (tested).
4. The only new stored identifier is the 8-byte alias fingerprint, one-way.
5. `retired_aliases` and `retired_tokens` are global (not link-scoped) and keep
   growing; they contain hashes only.
